## What this revises

v1 rested on five fixtures, one of which seeded a convention true only in
this repository. v2 adds two more such fixtures and a fourth arm. Three of
v1's claims change.

| v1 claim | v2 |
|---|---|
| A conventions file cannot move a rule true only in this repository | **Retracted.** It moves them as much as generic rules, 13/15 to 5/15 against 17/20 to 8/20, both p≈0.008. |
| The outcome is mostly determined by what was read first (17/18 vs 3/7) | **Weakened.** 23/24 against 7/11, p=0.026. Seven of eleven trials that found a compliant example copied anyway. |
| The gate is the most expensive arm | **Reversed.** Blocking before the write costs less than reporting after it, 6 turns against 7. |

The first is the one to read carefully. v1 drew a general claim about
repository-local conventions from a single fixture, `schedule-run`. With
three, `schedule-run` is the outlier rather than the rule: `refund-order`
goes 5/5 to 1/5 and `not-found` goes 4/5 to 0/5 under the same document.

## Discussion

Marked as inference. The results above stand on their own; what follows may
not.

**Documentation is unreliable in a way that depends on the task; enforcement
is not.** The `docs` column runs 0, 0, 5, 3, 4, 1, 0 across seven fixtures.
The `eslint` column is zero seven times. Same rules, same repository, same
model; the difference is whether the rule is checked or only written down.

**Where a document fails, the task itself argues for the shortcut.** The two
fixtures the document cannot move are `exports-summary`, which is generic,
and `schedule-run`, which is local. `exports-summary` hands the agent a
request body and a literal response shape, so `any` is close to forced;
`schedule-run` needs the current time, and `new Date()` is the obvious route
unless the Clock is already known. In `refund-order` and `not-found` the
compliant path is an API call and nothing in the task pushes against it.
This fits all seven fixtures. The local/generic split fits four.

It is a hypothesis formed after seeing the data and has not been tested
against fixtures designed for it.

**Timing matters less than we expected.** `eslint` and `lint-after` run the
same configuration at different moments and are indistinguishable on outcome
at this size (p=0.114), with the pre-write gate marginally cheaper. Both cost
about two turns more than doing nothing, which is the price of not shipping
the shortcut.

## Threats to validity

**Construct.** "Introduced a lint finding" is a proxy for "copied the
shortcut". They diverge: one `none`/`fetch-invoices` trial avoided the `as`
cast and returned an unsafe value instead. Both rates are recorded; the
tables above count the fixture's declared rule.

**Internal.** `jwt-issuer`'s prompt opens by naming `src/config/`, the
directory holding both the stale and the clean file, so its read pattern is
partly assigned rather than observed. The read-path result is correlational:
the design does not establish direction, and a trial disposed to write good
code may also be disposed to look around.

**External.** One model, one agent CLI version, one repository, seven
fixtures. Three fixtures were cut during construction and are described in
the README; `customer-orders` was cut after three attempts because its
compliant answer did not compile, which the validator did not catch until a
fifth check was added.

**Statistical.** Five repetitions per cell. 3/5 against 5/5 is p=0.44, so
per-fixture cells are descriptive. Pooled arms are 35 trials each. The
local-only read-path row has three trials in its exemplar cell and says
nothing.

## Method note carried forward

Seven checks in this project have run green while measuring nothing: five
`PreToolUse` gates, a fixture screen that could not distinguish a hard
fixture from an impossible one, and the probe check added to catch that
class, which wrote its probe to a dotfile TypeScript never compiled. Each was
found by trying to make it fail rather than by reading it. The validator now
runs five checks per fixture and each has been shown to fail on purpose.
